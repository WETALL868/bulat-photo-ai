## 2. Заключение: **условный GO при трёх исправлениях**

Снимок показывает качественно другой продукт, чем тот, что я проверял 01.10.
**Оба дефекта P0 прошлого аудита исправлены на сервере**, причём правильно:
быстрый заказ стал заявкой с `delivery.method=manager`, ошибку API видно
покупателю. СДЭК переведён на разрешённые тарифы с минимумом 300 ₽, и эта
логика — одна и та же в интерфейсе и при подтверждении заказа. Оплата,
кабинет и админка построены грамотно: webhook перепроверяет платёж в API
ЮKassa и не верит телу уведомления, сессии на selector+verifier, пароли через
`password_hash`, попытки входа ограничены таблицей `auth_attempts`.

Блокирует запуск не качество кода, а три конкретные вещи:

1. **Приём заказов не ограничен по частоте и не идемпотентен** (P0-1). Двенадцать
   заказов подряд приняты, одна корзина с одним ключом создала три заказа.
2. **`db/schema.sql` в webroot не соответствует боевой базе** (P1-1): в нём нет
   `payments`, `payment_events`, `order_delivery_details`. Восстановление базы
   по этому файлу даст магазин без оплаты и без деталей СДЭК.
3. **Нумерация заказов держится на одном файле** `var/orders/.counter` (P1-3).
   Его потеря ломает приём заказов, потому что в базе номер уникален.

Всё три чинятся за часы, не требуют переделок и проверяемы. После них —
GO, при условии, что внешние интеграции подтверждены на сервере (раздел 6).

## 4. Дефекты

### P0 — блокирует запуск

**P0-1. Приём заказов не ограничен по частоте и не идемпотентен.**
Файл: `site/api/index.php`, маршрут `order` (строки 536–780). Ограничитель
частоты есть только у `stock-alert` (строки 470–486) — у заказа, отзыва,
обратного звонка и расчёта СДЭК его нет.
Воспроизведение на изолированном стенде:
```
12 × POST /api/order (корзина, самовывоз) → 200 200 200 200 200 200 200 200 200 200 200 200
3 × POST /api/order (одна корзина, idempotencyKey одинаковый) → №900016, №900017, №900018
8 × POST /api/delivery/quote → все приняты
```
Ожидалось: повтор той же корзины даёт тот же номер; поток запросов с одного
адреса упирается в ограничитель.
Фактически: три заказа у менеджера вместо одного; бот за минуту заполняет
`var/orders`, таблицу `orders` и почтовый ящик. Расчёт СДЭК вдобавок тратит
квоту внешнего API — режим боевой (`cdek.test = false`).
Почему это P0 именно сейчас: при включённой онлайн-оплате дубль заказа — это
дубль платежа и разбирательство с покупателем, а не просто лишняя строка.

### P1 — чинить до запуска

**P1-1. `db/schema.sql` в webroot не соответствует боевой базе.**
Файл: `site/db/schema.sql` против `production-schema.sql`.
Отсутствуют три таблицы: `payments`, `payment_events`, `order_delivery_details`.
Восстановление или развёртывание второй среды по этому файлу даст базу, в
которой онлайн-оплата и детали СДЭК падают на первом же заказе. Сам файл
закрыт от сети (`.htaccess` строка 35), так что это не утечка, а расхождение
источника правды.

**P1-2. Нет ограничителя на `/api/delivery/quote`.**
Файл: `site/api/index.php`, строки 152–179. Проверка `hb_cdek_same_origin()`
(`cdek.php:385-392`) возвращает `true`, когда заголовок `Origin` отсутствует —
то есть для любого запроса не из браузера. Каждый вызов идёт в боевой API СДЭК
и делает запрос в MySQL.

**P1-3. Нумерация заказов держится на одном файле вне резервной копии.**
Файл: `site/api/index.php`, строки 695–708 — номер берётся из
`var/orders/.counter`. В базе есть таблица `order_counters` и функция
`hb_next_order_number()` (`order-store.php:11-29`), **но она не вызывается
нигде** — проверено поиском по всему снимку. В базе при этом
`UNIQUE KEY ux_orders_number` (`production-schema.sql:231`).
Следствие: потеря или сброс `.counter` (файл исключён из снимка, то есть и из
этой копии) приводит к повторной выдаче номеров; вставка в `orders` падает на
уникальном ключе; при включённом `database_required` каждый заказ получает 503
до ручного поднятия счётчика. Одновременно JSON-файл заказа перезаписывается
тем же именем — прежний заказ теряется.

### P2 — после запуска, но скоро

**P2-1. `ops/hiblack-vtt/mapping.json` отдаётся наружу.**
122 КБ соответствий «код магазина → код поставщика» на 3 636 товаров.
`.htaccess` (строка 35) закрывает `db`, `tools`, `var`, `catalog-source`,
`server`, но не `ops`. Проверено запросом к стенду: 200.

**P2-2. Новые файлы `api/` не внесены в запрет `.htaccess`.**
`FilesMatch` (строки 77–79) перечисляет только `admin`, `reviews-store`,
`config-path`, `shop.config.sample`. Новые `auth.php`, `cdek.php`, `db.php`,
`order-store.php`, `yookassa.php` защищены лишь стражем `HB_API` внутри кода —
это работает, пока PHP исполняется. При сбое обработчика (обновление панели,
правка конфигурации) исходники с логикой оплаты отдались бы текстом.

**P2-3. Нет ограничителя на отзыв и обратный звонок.**
`index.php`, маршруты `review` (строки 330–420) и `callback` (строки 280–310).
Та же картина, что у заказа: очередь модерации и почта набиваются без помех.

### P3 — гигиена

**P3-1.** `hb_next_order_number()` — мёртвый код, вводящий в заблуждение:
читающий решит, что номера выдаёт база.
**P3-2.** Нет ограничителя и проверки источника на `payment/webhook/yookassa`
(`index.php:241-253`). Содержимое перепроверяется в API ЮKassa, поэтому подделка
не проходит, но поток уведомлений вызывает поток исходящих запросов.

## 6. Не проверено — доступа нет

Ни по одному пункту нельзя сказать «работает»; формулировка — «не проверено».

* **Боевой сервер целиком**: `hiblack-msk.ru` из этой среды закрыт прокси (403 CONNECT).
* **MySQL**: сервера СУБД в среде нет, схему читал статически; запись через
  `order-store.php` в настоящие таблицы не выполнялась.
* **СДЭК**: настоящий API не вызывался — транспорт подменён заглушкой.
  Контрольные значения 300 ₽ и 375 ₽ подтверждены **арифметически** на боевом
  коде, но не сверкой с ответом СДЭК. Не проверены: действующий договор,
  доступность тарифов 136 и 368 по этому договору, фактическая цена сдачи
  отправления в московском пункте.
* **ЮKassa**: ключи исключены, платёж не создавался, webhook не вызывался.
  Режим (`test`/`production`) в снимке обезличен.
* **SMTP**: письма не отправлялись. Доставляемость, SPF, DKIM, попадание в спам
  не проверены. Код использует `mail()`, а не аутентифицированный SMTP.
* **Значение `database_required`**: обезличено. От него зависит поведение при
  недоступности MySQL — отказ в приёме заказа (fail-closed) либо запись только
  в JSON без строки в базе и без заказа в кабинете покупателя.
* **Резервные копии и откат**: механизма в снимке не видно; восстановление не проверялось.
* **Cron и синхронизация с поставщиком**: расписание и журнал ошибок не проверялись.

## 7. Предлагаемые исправления (отдельным списком, по порядку)

1. **Ограничитель частоты для всех POST-маршрутов.** Вынести логику из
   `stock-alert` (`index.php:470-486`) в функцию `hb_rate_limit($dir, $bucket,
   $limit, $window)` и применить: заказ — 10/час на адрес, расчёт СДЭК — 60/час,
   отзыв и звонок — 5/час. Превышение → 429 с понятным текстом.
2. **Идемпотентность заказа.** Клиент кладёт в тело `idempotencyKey` (uuid,
   живёт до успешной отправки). Сервер хранит `key → number` рядом со счётчиком
   и при повторе возвращает прежний номер, ничего не создавая. В базе —
   колонка `orders.idempotency_key` с уникальным ключом.
3. **Привести `db/schema.sql` к боевой базе** — добавить `payments`,
   `payment_events`, `order_delivery_details`; завести запись в
   `schema_migrations` и правило «схема в webroot обновляется вместе с миграцией».
4. **Нумерация из базы.** Включить `hb_next_order_number()` как источник номера,
   файл `.counter` оставить запасным путём на случай недоступности MySQL.
   Добавить в выкладку проверку «максимум `orders.order_number` ≥ значения счётчика».
5. **Закрыть `ops/`** в `.htaccess` (добавить в список строки 35) и внести новые
   `api/*.php` в `FilesMatch` строки 77.
6. **Подтвердить внешние интеграции** по разделу 6 и записать результат рядом с
   этим отчётом: режим ЮKassa, договор СДЭК, доставляемость письма,
   значение `database_required`.
7. **Резервная копия и откат**: ежедневный дамп MySQL + `var/`, проверенное
   восстановление, записанный порядок отката версии.
8. **P2-3 и P3** — после запуска.
