### Важная поправка к моему отчёту `AUDIT-SEO-SECURITY-2026-10-08.md`

## 3. Находки

### P2-1. Файл сопоставления с поставщиком читается публично

**Адрес:** `https://hiblack-msk.ru/ops/hiblack-vtt/mapping.json` → 200, 125 091 байт.

Сама папка `/ops/` закрыта (403), а файл внутри отдаётся. В нём 3636 записей вида
«внутренний номер товара → код поставщика». Паролей, ключей, цен и персональных данных внутри нет —
я проверил поиском по именам полей, ничего из этого не нашлось. Но по самому пути (`hiblack-vtt`)
и содержимому восстанавливается, у кого магазин закупается и под какими артикулами. Вы отдельно
просили не публиковать приватные данные B2B — поэтому выношу отдельно.

**Как воспроизвести:** `curl -s https://hiblack-msk.ru/ops/hiblack-vtt/mapping.json | head -c 200`

**Решение:** закрыть не только листинг, но и файлы. В `.htaccess` в корне:

```apache
RedirectMatch 404 ^/ops(/|$)
```

или перенести `ops/` за пределы webroot. После правки `/ops/hiblack-vtt/mapping.json` должен
отдавать 404, а сайт — работать без изменений: клиент этот файл не запрашивает (проверено,
в `app.cdek1.js` обращений к нему нет).

### P2-2. Нет Content-Security-Policy

Единственный заголовок безопасности, которого не хватает. Без CSP любой внедрённый скрипт
(через отзыв, через стороннюю библиотеку, через скомпрометированный хостинг) выполнится без помех.
Для магазина с онлайн-оплатой это основная оставшаяся линия обороны.

Сайт подключает ровно четыре своих скрипта, шрифты с себя же и один внешний домен — Метрику.
Политика получается короткой. Начните в режиме наблюдения, чтобы ничего не сломать:

```apache
Header always set Content-Security-Policy-Report-Only "default-src 'self'; script-src 'self' 'unsafe-inline' https://mc.yandex.ru; img-src 'self' data: https://mc.yandex.ru; style-src 'self' 'unsafe-inline'; font-src 'self'; connect-src 'self' https://mc.yandex.ru; frame-src https://yandex.ru https://mc.yandex.ru; frame-ancestors 'self'; base-uri 'self'; form-action 'self'"
```

`'unsafe-inline'` в `script-src` нужен из-за встроенного блока `window.HB_BOOTSTRAP` — без него
страницы перестанут работать. Через неделю наблюдения, если нарушений нет, замените
`Content-Security-Policy-Report-Only` на `Content-Security-Policy`.

Карта Яндекса на странице контактов грузится во фрейме с `yandex.ru` — поэтому `frame-src` включён.

На товарных страницах `Product`/`Offer` есть и он корректен. Остального нет:

### P2-4. Кэширование настроено против себя

Три числа:

| Ресурс | Сейчас | Проблема |
|---|---|---|
| HTML страницы | `no-store, max-age=0` | 110–115 КБ (gzip) заново при каждом переходе по сайту |
| `/assets/*.js`, `*.css`, `*.webp` | `max-age=86400` | адреса уже содержат `?v=…`, можно кэшировать год |
| `/data/catalog/index.json` | `no-cache, must-revalidate` | 208 КБ (gzip), проверка на каждой странице |

Первая загрузка товарной страницы — **510 КБ по сети без картинок**, плюс два спрайта-атласа
(`atlas-1.webp` 268 КБ и `atlas-8.webp` 428 КБ). Для мобильного интернета это много.

Отдельно: цены приезжают дважды. Они уже встроены в HTML (`window.HB_BOOTSTRAP`, 519 КБ в
исходном виде — именно из-за него страница весит 580–616 КБ), и тут же клиент качает
`/api/storefront` (50 КБ gzip) с теми же данными.

**Что сделать, по убыванию эффекта:**

1. Статику с `?v=` — на год: `Header set Cache-Control "public, max-age=31536000, immutable"` для
   `/assets/`. Безопасно: при смене файла меняется `?v=`.
2. HTML — разрешить короткий кэш вместо `no-store`: `Cache-Control: private, max-age=60, must-revalidate`.
   Цены при этом не устареют: минута — меньше интервала обновления прайса.
3. Проверить, нужен ли запрос `/api/storefront`, если те же цены уже встроены в страницу.
4. Атласы — нарезать или перевести иконки в SVG-спрайт; 700 КБ изображений ради иконок много.
5. Добавить `Vary: Accept-Encoding` на HTML — сейчас его нет, это мешает кэшированию на промежуточных узлах.

Запуску это не мешает, но прямо влияет на Core Web Vitals, а значит на позиции.

### P3 — мелочи

| № | Что | Решение |
|---|---|---|
| P3-1 | HSTS без `includeSubDomains` и `preload` | `max-age=31536000; includeSubDomains; preload` — но только когда уверены, что **все** поддомены работают по HTTPS |
| P3-2 | Страница 403 показывает `Apache/2.4.58 (Ubuntu)` | `ServerSignature Off` и `ServerTokens Prod` в конфиге Apache, либо свой `ErrorDocument 403` |
| P3-3 | У всех 8016 адресов в sitemap `lastmod` 2026-09-27, хотя сайт менялся 03.10 и 08.10 | проставлять дату фактического изменения страницы — Яндекс и Google по ней решают, что перечитывать |
| P3-4 | Title товара до 87 символов | укоротить до ~65: выдача обрежет остальное |
| P3-5 | Нет meta `google-site-verification` | если Search Console ещё не подключен — подключить; если подключен через DNS, пункт закрыт |
| P3-6 | Метрика грузится до нажатия «ОК, согласен» | баннер информирующий, а не запрашивающий. Для Метрики (российский сервис, без трансграничной передачи) практика это допускает, вебвизор и карта кликов у вас выключены. Если хотите строго — запускать счётчик после согласия |
| P3-7 | Нет brotli | включить `brotli` в nginx: даст ещё 15–20 % к gzip |
| P3-8 | `/favicon.ico` → 404 | положить 32×32 `.ico` в корень: часть браузеров и роботов спрашивает именно его |
| P3-9 | `/404` отдаёт код 200 | адрес закрыт `noindex` и нигде не используется, так что вреда нет; для чистоты — отдавать 404 |
| P3-10 | 44 товара с `Product` без блока `offers` | Search Console покажет предупреждение «отсутствует поле offers». Можно добавить `offers` с `availability: PreOrder` без цены — или оставить как есть, цену выдумывать нельзя |

## 4. Что осталось непроверенным и почему

| Пункт | Почему |
|---|---|
| Редирект `http://` → `https://` | агентский прокси в моей среде пропускает только HTTPS. HSTS на год закрывает это для всех, кто уже заходил |
| Ограничение частоты заказов и идемпотентность `/api/order` | проверка требует отправки настоящих заказов на боевой сервер — вы это запретили, и правильно. Находка из снимка 02.10 (12 заказов подряд приняты, одна корзина дала три заказа) **остаётся в силе**, пока Codex не проверит на стенде |

| Вход в админку и кабинет | пароли не подбирал, в админку не входил |
| Серверный код в текущем состоянии | снимок у меня от 02.10, а сервер менялся как минимум 03.10 и 08.10. Все выводы о коде относятся к снимку; выводы в этом отчёте — к тому, что сервер отдаёт сегодня |
| Реальная скорость загрузки | мои замеры (2,2–4,6 с) сняты через прокси и к реальным условиям покупателя отношения не имеют. Нужен PageSpeed Insights или Яндекс.Метрика |

## 5. Что я предлагаю сделать по порядку

**До того, как звать трафик:**

1. Закрыть `/ops/` целиком (P2-1) — две минуты, одна строка в `.htaccess`.
2. Включить CSP в режиме наблюдения (P2-2).
3. Проверить в Search Console, подтверждены ли права Google (P3-5).

**В первую неделю:**

4. Добавить `BreadcrumbList` и `Organization` (P2-3) — самый заметный эффект в выдаче.

## 6. Заключение

**GO.** Сайт можно открывать для покупателей и поисковиков.

Блокирующих находок на живом сервере нет. Главная из прежних тревог — расхождение цен в
микроразметке — на боевом сервере не подтвердилась: цены в разметке совпадают с живым прайсом.
Защита служебных файлов, заголовки безопасности, TLS, правила индексации и канонические адреса
настроены правильно.

Единственное, что я бы поправил до прихода трафика, — публично читаемый `mapping.json` (P2-1):
это не дыра в безопасности, но это ваши коммерческие данные, и закрывается одной строкой.

Открытым вопросом остаётся защита `/api/order` от повторных и частых отправок — проверить это
на боевом сервере я не мог и не стал. Это единственное, что я бы рекомендовал закрыть
до крупных рекламных кампаний, когда поток заказов вырастет.
